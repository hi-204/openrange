# OpenRange — Architecture

Status: **design (pre-M0)**. Sections marked *(planned)* describe intent, not code.
When the code disagrees with this file, the code is checked against the decision log and
one of them is fixed — never silently.

## 1. solver-core

Pure library. No file system, no network, no global mutable state, no clock. Everything
that needs randomness takes an explicit seed. Compiles for `wasm32-unknown-unknown` and
native. Multithreading is an optional cargo feature (`parallel`, uses rayon) enabled only
by the CLI.

### 1.1 Cards and combos
- `Card(u8)`: `rank * 4 + suit`, rank 0 = deuce … 12 = ace, suit 0..3 = c, d, h, s.
- `CardSet(u64)` bitmask for dead-card and overlap checks.
- **Combo index** 0..1326 for every unordered pair `(c1 < c2)`; a fixed lookup table in both
  directions. A range is `[f32; 1326]` of weights in [0, 1].
- **Hand classes**: 169 (13 pairs, 78 suited, 78 offsuit) with grid coordinates for the
  13×13 UI; mapping class ↔ combos.

### 1.2 Hand evaluator
- Output: `Strength(u16)`, higher is better, ordered exactly like poker hand values;
  `category = strength >> 12` (0 high card … 8 straight flush). 7,462 distinct values.
- 7 cards: count suits; if any suit has ≥ 5 cards, look up its 13-bit rank mask in an
  8,192-entry flush/straight-flush table. Otherwise the rank-count multiset, encoded as
  Σ 5^rank (unique because counts are ≤ 4, and buildable one card at a time via `HandKey`),
  is looked up in a 2^17-slot open-addressing table holding every multiset of 5–7 cards
  (~74k keys). Table values come from direct rank logic; the slow reference evaluator is an
  independent cross-check. Tables are built at runtime (a few ms, ~800 KB of memory) so
  nothing large is committed. Measured: ~67 M seven-card evaluations/s single-threaded (native).
- Reference evaluator (slow, obviously-correct best-of-21 five-card scoring) lives in the
  test code and in `solver-core::eval::reference` for property tests.
- Tests: full 133,784,560 seven-card enumeration with exact category counts (release mode,
  marked `#[ignore]` in debug, always run in CI and by `solver-cli validate`); random 7-card
  agreement with reference; 5- and 6-card variants.

### 1.3 Ranges
- Parser for comma-separated tokens: pairs `QQ`, `22+`, `99-66`; suited/offsuit `AKs`, `A2s+`,
  `KTo+`, `T9s-54s`; unsuited `AK` (= both); specific combos `AhKh`; weights `token:0.5`.
- Printer produces the shortest canonical string for a range (weights grouped).
- Round-trip property: `parse(print(r)) == r` for random ranges; `print(parse(s))` is
  canonical-equivalent to `s`.
- Exposed through WASM so the UI never re-implements parsing (single source of truth).

### 1.4 Equity
- Exact enumeration over remaining board cards when the count is small (turn/river always,
  flop for hand-vs-hand and modest ranges); seeded Monte Carlo otherwise, reporting standard
  error. Hand vs hand, hand vs range, range vs range, multiway, dead cards.
- Range-vs-range uses combo weights with card-removal (impossible pairs excluded).
- 169×169 preflop table: exact over all 1,712,304 boards per suit-isomorphic combo pair
  (47,008 classes), aggregated to classes with correct combo weighting; generated by
  `solver-cli gen-equity` into `data/equity/preflop-169.json` (~160 s on 24 threads).
- Checks: AA vs random ≈ 85.2 %; eq(A,B) + eq(B,A) = 100 % (ties split); known spot values
  are *computed and compared to themselves across methods* (exact vs MC within 4σ), never
  typed in.

### 1.5 Suit isomorphism
- Canonicalize a board under the 24 suit permutations; compute the board's stabilizer
  (permutations that map the board to itself).
- Used for (a) collapsing chance outcomes on turn/river deals with multiplicity weights,
  (b) mapping strategies between isomorphic boards (aggregated reports), (c) tests.

### 1.6 RNG
- Own SplitMix64 / xoshiro256** implementation so seeded results never change because a
  dependency was upgraded (see D-013).

### 1.7 Tabular CFR (validation games)
- Generic `Game` trait (histories, information sets, chance, utilities) for Kuhn and Leduc.
- Algorithms share one `RegretRule` module: **DCFR** (positive regrets × tᵅ/(tᵅ+1), negative
  × tᵝ/(tᵝ+1), strategy sum × (t/(t+1))ᵞ, α = 1.5, β = 0, γ = 2) and **CFR+** (regrets
  floored at 0, linear averaging with configurable delay). Alternating updates.
- The current strategy σᵗ is snapshotted once per pass: an infoset sits at many tree nodes
  (one per hidden chance outcome) and all of them must use the same σᵗ while its regrets
  accumulate. CFR+ flooring and DCFR discounting are applied after the pass.
- Exact best response by tree walk with per-infoset action choice (memoized, deepest first)
  → exploitability; cross-checked against brute force over all pure strategies on Kuhn.
- Implemented in `solver-core/src/cfr/tabular.rs`; games in `solver-core/src/games/`.

### 1.8 Postflop solver
**Game tree** (`tree`): built from a `TreeConfig`: starting street, pot, effective stack,
board, bet sizes per street × player × (first bet | raise) as % pot (plus "all-in"),
add-all-in threshold (if a bet would put > X % of the remaining stack in, replace/add all-in),
force all-in when remaining stack < Y % of pot, max raises per street, donk-bet toggle,
rake (% + cap + no-flop-no-drop). Node kinds: `Action { player, actions }`,
`Chance { street }`, `Terminal { Fold(winner) | Showdown }`. Pot and bets tracked in chips
(1 bb = 100 internal units to keep sizes integral and deterministic).

**Hands per player**: from each range, drop combos that conflict with the board; keep only
non-zero weights. Hands are stored in a per-player list; all vectors are indexed by that list.

**Storage per action node** (`n_actions × n_hands_of_acting_player`): cumulative regret and
cumulative strategy (f32). Optional 16-bit compressed storage with a per-row scale (M4) when
memory is tight. Laid out in one arena allocation sized by the memory estimator.

**Traversal** (alternating updates, one traversal per player per iteration):
`cfv = walk(node, traverser, opp_reach[])` returns counterfactual values for every traverser
hand at once.
- Traverser's node: σ from regret matching; recurse per action; node value = Σ σ·child;
  regrets += child − node value (then discounting per algorithm).
- Opponent's node: recurse with `opp_reach × σ_opp(a)`; sum children; accumulate the
  opponent's average-strategy sums with its own reach (tracked alongside).
- Chance node: for each canonical dealt card, zero hands that contain it, recurse, weight
  by multiplicity / number of possible cards, sum. Native CLI may parallelize over chance
  children; results summed in a fixed order so output is identical to single-threaded.
- Terminal: see below.

**Terminal evaluation in O(n)** (per node, both lists pre-sorted by river strength):
- *Showdown:* sweep opponent hands in strength order maintaining `total_less` and
  `card_less[52]` (opponent reach weakers, total and per card). For hero hand h = (c1, c2):
  `win_reach = total_less − card_less[c1] − card_less[c2]` (an identical combo can't be
  strictly weaker, so no add-back is needed). Symmetric pass for `lose_reach`; ties fall
  out as the remainder. `cfv[h] = win_reach · win_payoff + lose_reach · lose_payoff +
  tie_reach · tie_payoff`.
- *Fold:* `reach = total − card[c1] − card[c2] + same_combo(h)` (inclusion–exclusion; the
  identical opponent combo was subtracted twice).
- Rake is applied to the pot at terminals; no-flop-no-drop is a flag that zeroes rake for
  hands ending preflop (preflop solver only).

**Exploitability**: best response for each player against the opponent's *average*
strategy via the same vectorized walk (max instead of mix at the BR player's nodes).
Defined generally as `NashConv / 2 = Σᵢ (BRᵢ − uᵢ(σ̄)) / 2`, which stays correct with rake
(non-constant-sum). Reported in chips, bb, and % of starting pot. A solve stops at target
exploitability or iteration cap, whichever comes first; exploitability is checked every
k iterations (it costs about one iteration).

**Memory estimator**: builds the tree in count-only mode and sums
`Σ_action-nodes n_actions · n_hands · bytes_per_entry · 2` + chance/terminal scratch +
sorted strength tables per runout + fixed overhead. Shown before solving; refuses above the
budget with concrete suggestions (fewer sizes, lower raise cap, compressed storage, native CLI).

**Abstraction ladder** (flop, when over budget) *(planned, M4)*: (1) compressed storage,
(2) cap raises per street at 1 on turn/river, (3) one bet size per street on turn/river,
(4) one bet size on flop. The chosen step is stored in the result and shown as a warning.

**Determinism**: no RNG in full-traversal CFR; fixed summation order; no `f32::mul_add`;
tests assert bit-identical results for identical inputs and seed. Native-vs-WASM equality
is tested via golden hashes.

### 1.9 Preflop *(planned, M5)*
- **Push/fold**: per-combo (1326) decisions with exact all-in equities; heads-up solved by
  full CFR to near-zero exploitability (chip EV and ICM via Malmuth–Harville). 3–6 players:
  CFR with sampled multiway equities, labeled approximate with measured per-player BR gain.
- **Tier B EQR tree**: preflop action tree for 6-max 100 bb (and 20/40/60 bb); when action
  closes and a flop is seen, terminal value = pot × equity × EQR(position, initiative, pot
  type, hand class) − investment. EQR v1 parameters are *authored model inputs* (documented,
  labeled); EQR v2 calibrates them from our own postflop solves. Sensitivity report shows how
  charts move when EQR parameters change.

### 1.10 ICM *(planned, M5)*
Malmuth–Harville finishing probabilities, exact for ≤ 9 players by recursion with memoization.

## 2. solver-cli

`solver-cli solve <spot.json>`, `solver-cli validate [--quick]`, `solver-cli gen-equity`,
`solver-cli gen-charts <family>`, `solver-cli gen-goldens`. All generation is
deterministic and writes provenance (including `git rev-parse HEAD` and a dirty flag passed
by the calling Node script). `validate` writes `docs/VALIDATION.md`.

## 3. solver-wasm

Thin wasm-bindgen layer. Requests and responses are JSON strings (handled in
`solver-wasm/src/api.rs`, unit-tested natively). Current exports: `version()`,
`parseRange(text)`, `equity(requestJson)` — "auto" mode enumerates exactly for two players
when the work estimate is ≤ 3·10⁷ evaluations, otherwise uses seeded Monte Carlo.
Planned stateful solver handle (M3+); large arrays will move to typed arrays then:

```
new Solver(configJson) -> handle          // builds tree, validates config
handle.memoryEstimate() -> bytes
handle.allocate()                          // throws a typed error if over budget
handle.step(iterations) -> { iteration, exploitability? }
handle.exploitability() -> { chips, bb, pctPot }
handle.nodeStrategy(nodePath) -> Float32Array + action labels
handle.free()
```

Built with `cargo build --target wasm32-unknown-unknown --release` then the pinned
`wasm-bindgen` CLI (`--target web`). Output committed in `web/public/wasm/`.

## 4. Worker protocol (web)

One long-lived module worker per heavy task type (solver, equity). Messages are typed:

```
UI → worker: init · solve{config} · step{n} · pause · resume · cancel · query{node}
worker → UI: ready · estimate{bytes, fits} · progress{iter, exploitability, elapsedMs}
             · done{summary} · result{…} · error{code, message, diagnostics}
```

The worker runs iterations in small chunks (~50–100 ms) and yields between chunks, so
pause/cancel messages are handled promptly. Cancel = stop + free; if a chunk ever hangs,
the UI terminates and recreates the worker. Errors carry a beginner-readable message and a
diagnostics object with no personal data.

- State: Zustand stores per feature; persistent data in Dexie (`settings`, `lessonProgress`,
  `quizResults`, `srsCards`, `drillAttempts`, `notes`, `savedSpots`, `handHistories`).
  Export/import is a single versioned JSON document.
- Data files from `data/` are copied into `web/public/data/` by a Node script before
  `dev`/`build` (that copy is git-ignored). Lessons are bundled via `import.meta.glob`.
- Large data is stored gzip-compressed and decoded with the browser's built-in
  `DecompressionStream` (no extra dependency).
- No code path may call `fetch` on a non-same-origin URL; a Vitest check scans the bundle
  and a Playwright test asserts no external requests.

## 6. Data formats

**Provenance block** (embedded in every chart/spot/golden file):

```json
{
  "schema": "openrange.provenance/1",
  "source": "solver_exact | solver_approx | authored",
  "generator": "solver-cli gen-charts pushfold-hu --stack 10",
  "solver": { "algorithm": "dcfr", "alpha": 1.5, "beta": 0, "gamma": 2,
              "iterations": 5000, "exploitability": { "bb": 0.0004, "pctPot": 0.003 } },
  "model":  { "name": "eqr-v1", "params": { } },
  "abstraction": null,
  "seed": 42,
  "generatedAt": "2026-10-24T00:00:00Z",
  "gitCommit": "abc1234", "gitDirty": false,
  "notes": "why this is approximate, if it is"
}
```

**Chart file**: provenance + game description + `strategy[169 or 1326][actions]` +
optional `ev[...]` (bb). **Spot file** (postflop drills, workbench saves): provenance +
tree config + ranges + quantized strategies/EVs for stored nodes. **Lesson**: Markdown with
YAML front-matter (`id, level, title, minutes, prerequisites, drills, glossary`), fenced
` ```widget <name> {json} ` blocks for interactive components, `$…$` / `$$…$$` math.

## 7. Grading *(planned, M6)*

- EV loss = EV(best action) − EV(chosen action) for this exact hand at this node, in bb
  (preflop) and % pot (postflop). Mixed strategies are handled naturally: at equilibrium all
  actions in the support have (near-)equal EV, so a 30 % action shows tiny EV loss and is
  labeled "lower-frequency", not a mistake.
- Tolerance accounts for solve accuracy: anything within the spot's exploitability-derived
  noise floor counts as Best.
- Default thresholds (tunable, revisited in M6): preflop Best ≤ 0.02 bb · Acceptable ≤ 0.10 ·
  Inaccuracy ≤ 0.30 · Mistake ≤ 1.0 · Blunder > 1.0; postflop Best ≤ 1 % pot · Acceptable
  ≤ 3 % · Inaccuracy ≤ 8 % · Mistake ≤ 20 % · Blunder > 20 %.
- Explanations are assembled from computed features (equity vs range, pot odds needed vs
  offered, blockers, SPR, texture class, range/nut advantage, MDF). Each feature sentence
  has a predicate; tests generate many spots and assert no sentence contradicts the numbers.
- Stats show Wilson intervals and say "not enough data yet" below a minimum sample size.
